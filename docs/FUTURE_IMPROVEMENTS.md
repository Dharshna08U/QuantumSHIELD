# Future Improvements and Advancement Roadmap

This roadmap separates near-term engineering from research and production work. Every item addresses a limitation present in this prototype; none should be described as already implemented. Difficulty is relative to this repository and assumes a small student team.

## Level 1 — Immediate Improvements

1. **Frontend component and browser tests** — Add focused component tests and a small browser smoke suite for login, incident detail, status changes, API errors, and navigation. This addresses the lack of a frontend test script and prevents UI/API regressions. **Difficulty: Medium. Project/paper: Strong project improvement; not a research contribution by itself. Infrastructure: CI runner; browser binary in CI.**
2. **More API and workflow coverage** — Add property/boundary cases for role permissions, failed integrations, audit completeness, CORS, schema validation, and concurrent condition polling. Existing tests are broad for backend logic but do not establish production behavior. **Difficulty: Medium. Project/paper: Strong engineering work; useful methodology support. Infrastructure: None beyond test CI.**
3. **Reproducible Python dependencies** — Pin a tested dependency set (for example, a constraints or lock file) and add a clean-environment install check. `requirements.txt` currently uses compatible ranges. **Difficulty: Easy–Medium. Project/paper: Project quality. Infrastructure: CI.**
4. **Document one canonical demo configuration** — Add a checked, secret-free demo environment file or script that selects deterministic mode and fixed local origins without production credentials. This reduces configuration drift between README, `.env.example`, and actual operation. **Difficulty: Easy. Project/paper: Strong reproducibility improvement. Infrastructure: None.**
5. **Frontend error and loading states** — Normalize API error responses and improve empty/loading/error rendering for simultaneous panel requests. This addresses confusing failures when one service is unavailable. **Difficulty: Medium. Project/paper: Project quality. Infrastructure: None.**
6. **Structured logs and request IDs** — Add safe structured logs, request correlation IDs, and explicit redaction tests. This addresses limited troubleshooting and log-scrubbing guidance. **Difficulty: Medium. Project/paper: Engineering; supports evaluation reproducibility. Infrastructure: Log collector optional.**
7. **AI evaluation report** — Split synthetic data into reproducible train/validation/test sets and publish per-class precision, recall, F1, confusion matrix, and limitations. This addresses the current demo dataset and absence of reported performance. **Difficulty: Easy–Medium. Project/paper: Strong baseline work. Infrastructure: None.**
8. **Probability calibration study** — Compare uncalibrated probabilities with calibration methods and held-out reliability diagrams before presenting confidence to operators. This directly addresses the UI's uncalibrated score. **Difficulty: Medium. Project/paper: Good experimental extension. Infrastructure: None.**
9. **Database backup/restore runbook** — Document SQLite backup consistency and PostgreSQL migration/backup restore checks. This addresses local DB loss and lack of recovery procedures. **Difficulty: Easy. Project/paper: Useful operations maturity. Infrastructure: Backup storage for deployment.**
10. **Lockfile and build hygiene** — Keep npm lockfiles in sync, use `npm ci`, and add an automated check that generated `dist`, model, and database files remain ignored. This makes builds reproducible and reduces accidental artifact commits. **Difficulty: Easy. Project/paper: Strong delivery hygiene. Infrastructure: CI.**

## Level 2 — Advanced Implementation

1. **Live liboqs integration validation** — Pin and test the supported liboqs/liboqs-python/toolchain combination for ML-DSA and ML-KEM against known vectors and negative cases. Current adapter code and test doubles do not prove a working native deployment. **Difficulty: Hard. Project/paper: Strong implementation milestone. Infrastructure: Native build tools and controlled CI image.**
2. **Key lifecycle for PQC** — Define generation, rotation, backup, access, recovery, and destruction of signing and KEM keys; keep private material outside source and database. Current keys are externally referenced with no lifecycle service. **Difficulty: Hard. Project/paper: Strong security-design component. Infrastructure: KMS/HSM or protected secret store.**
3. **ML-DSA signature deployment tests** — Validate key formats, algorithm identifiers, signatures, and verification across service restarts and version upgrades. Current code supports the path but demo mode reports unavailable. **Difficulty: Hard. Project/paper: Good systems evaluation. Infrastructure: liboqs runtime and protected test keys.**
4. **ML-KEM + authenticated encryption workflow** — Validate recipient key distribution, envelope format, nonce handling, decryption authorization, and ciphertext lifecycle with real keys. Current implementation derives an AES-256-GCM key from KEM material, but the live provider is not configured. **Difficulty: Hard. Project/paper: Strong integration milestone. Infrastructure: liboqs and secure key custody.**
5. **Fabric test network** — Deploy an isolated Fabric network, identities, endorsement policy, channel, chaincode, bridge, and failure/retry tests. Current adapter and chaincode source are not a deployed ledger. **Difficulty: Hard. Project/paper: Strong prototype extension. Infrastructure: Multiple Fabric peers/orderer, CA/identities, TLS, persistent volumes.**
6. **Ledger data-minimization and privacy analysis** — Review every committed field, retention requirement, access policy, and correction/deletion limitation before real network use. Current metadata is limited compared with source evidence but still includes operational and model fields. **Difficulty: Medium–Hard. Project/paper: Excellent security analysis. Infrastructure: Fabric test network and governance input.**
7. **PostgreSQL integration and migration tests** — Exercise migrations, transaction boundaries, locking, unique-fingerprint races, backup/restore, and pool behavior using PostgreSQL. SQLite is the only verified local database path. **Difficulty: Medium. Project/paper: Strong reliability work. Infrastructure: PostgreSQL service/CI container.**
8. **Read-only live Kubernetes adapter evaluation** — Test HTTPS, CA validation, RBAC, pagination, API versions, large clusters, throttling, and partial failures before enabling writes. Current tests use fakes and no cluster is included. **Difficulty: Hard. Project/paper: Strong operational evaluation. Infrastructure: Disposable Kubernetes cluster and least-privilege service account.**
9. **Safer remediation integration tests** — In an isolated disposable cluster, test allowlists, approvals, request replay, timeouts, convergence, and rollback/no-op behavior with explicit gates. Current simulation is the recommended verified path. **Difficulty: Hard. Project/paper: Strong controlled-safety result. Infrastructure: Disposable Kubernetes cluster.**
10. **Larger, representative threat dataset** — Build a labeled, permission-cleared dataset with documented provenance, class balance, and a held-out source split. The current bundled examples are synthetic and too small for operational claims. **Difficulty: Hard. Project/paper: Essential for meaningful ML evaluation. Infrastructure: Data governance and secure storage.**
11. **Model versioning and rollback** — Store model metadata, dataset hash, training configuration, evaluation results, and previous approved model. The current service loads a local artifact path. **Difficulty: Medium. Project/paper: Strong reproducibility. Infrastructure: Artifact storage/registry.**
12. **Model drift monitoring** — Measure input distribution and post-incident label feedback, define thresholds, and alert for review rather than retrain automatically. There is no production feedback or drift process. **Difficulty: Medium–Hard. Project/paper: Good longitudinal study. Infrastructure: Metrics/time-series storage and reviewed labels.**

## Level 3 — Research Enhancements

1. **Explainable AI for incident triage** — Compare interpretable features or local explanations and present evidence with uncertainty. This addresses low transparency of bag-of-words LogisticRegression outputs. **Difficulty: Medium. Project/paper: Strong research candidate. Infrastructure: None for offline work.**
2. **Adversarial and robustness evaluation** — Test evasion, paraphrase, class imbalance, distribution shift, and poisoning risks using a documented threat model. This addresses the absence of adversarial evaluation. **Difficulty: Hard. Project/paper: Strong research candidate. Infrastructure: Evaluation compute and curated test cases.**
3. **Graph-based cross-resource threat detection** — Model relationships among pods, deployments, identities, events, and incidents; compare graph rules/embeddings to the present per-object thresholds. This could detect coordinated patterns missed by independent rules. **Difficulty: Hard. Project/paper: Strong novel extension if evaluated rigorously. Infrastructure: Graph store optional; dataset required.**
4. **Federated learning for multi-cluster institutions** — Train across organizations without centralizing raw telemetry and evaluate leakage, non-IID data, and poisoning. Current deployment is single database/service. **Difficulty: Hard. Project/paper: Strong research direction. Infrastructure: Multiple participants or realistic simulators and secure aggregation.**
5. **Privacy-preserving analytics** — Compare field minimization, aggregation, differential privacy, or secure computation for shared incident trends. This addresses the sensitive evidence and cross-organization data problem. **Difficulty: Hard. Project/paper: Strong research candidate with measurable privacy/utility trade-offs. Infrastructure: Privacy evaluation tooling and realistic data.**
6. **Zero-trust integration** — Prototype continuously evaluated workload/user identity, short-lived authorization, and context-based policy decisions. Current RBAC is role-based and local. **Difficulty: Hard. Project/paper: Good systems extension. Infrastructure: Identity provider and policy engine.**
7. **Decentralized identity for incident provenance** — Study verifiable organization/workload credentials for signed reports, with revocation and governance. Current actors are local SQL user rows. **Difficulty: Hard. Project/paper: Strong if tied to a clear trust model. Infrastructure: Identity issuer/verifier and key management.**
8. **Confidential computing** — Evaluate protected inference or evidence processing in trusted execution environments against a concrete threat model. No enclave or attestation path exists. **Difficulty: Hard. Project/paper: Research-heavy. Infrastructure: Supported hardware/cloud platform.**
9. **Advanced PQC provenance** — Compare hybrid classical/PQC signatures, algorithm agility, key rotation, and long-term verification evidence. Current optional adapter is a single configured provider path. **Difficulty: Hard. Project/paper: Strong cryptography systems study. Infrastructure: PQC runtime, key management, long-term test corpus.**
10. **Cross-cluster monitoring** — Correlate privacy-minimized conditions across clusters and measure false-positive/latency behavior. Current persistence and watcher are scoped to one configured provider/database. **Difficulty: Hard. Project/paper: Strong distributed-systems study. Infrastructure: Multiple clusters or faithful simulators.**
11. **Human factors and approval-policy experiment** — Measure analyst/operator agreement, decision time, alert fatigue, and safety under different explanations/approval rules. Current approval UI has no user study or policy outcome evaluation. **Difficulty: Medium–Hard. Project/paper: Strong applied research. Infrastructure: Ethics review/participants for human-subject work.**

## Level 4 — Production / Enterprise

1. **High-availability deployment** — Run stateless API replicas with durable database/ledger dependencies and tested failover. Current local setup is single-process oriented. **Difficulty: Hard. Project/paper: Enterprise work, not required for the prototype paper. Infrastructure: Orchestrator, HA database, load balancer.**
2. **Kubernetes-native deployment** — Package API, AI, watcher, and UI with health probes, resource limits, network policies, and least-privilege service accounts. Current Compose file provisions only PostgreSQL. **Difficulty: Hard. Project/paper: Optional system demonstration. Infrastructure: Kubernetes cluster and image registry.**
3. **Distributed watcher lease** — Add leader election/leases so multiple API replicas cannot all poll and duplicate work. Current watcher is a per-process lifespan task. **Difficulty: Hard. Project/paper: Strong scalability engineering. Infrastructure: Shared database or coordination store.**
4. **Secrets manager and HSM/KMS** — Replace filesystem/environment secret distribution with managed rotation and hardware-backed signing. Current references rely on operator-provided paths/tokens. **Difficulty: Hard. Project/paper: Essential for production, costly for student demo. Infrastructure: Cloud secrets service or HSM/KMS.**
5. **Central observability** — Add OpenTelemetry traces/metrics/logs plus Prometheus/Grafana dashboards and alerting with sensitive-field redaction. Current observability is basic health and application audit data. **Difficulty: Medium–Hard. Project/paper: Strong operational evaluation. Infrastructure: Collector and metrics/log storage.**
6. **SIEM/SOAR integration** — Add authenticated, idempotent connectors and delivery/retry controls to existing enterprise monitoring and response platforms. There are no external event connectors now. **Difficulty: Hard. Project/paper: Practical system extension. Infrastructure: SIEM/SOAR test tenant and connector credentials.**
7. **Enterprise SSO / OAuth2 / OIDC** — Delegate authentication to an identity provider, implement token lifecycle, group mapping, MFA, and audit of identity events. Current login is local username/password and JWT. **Difficulty: Hard. Project/paper: Production readiness. Infrastructure: OIDC provider.**
8. **Multi-tenant authorization** — Isolate organizations, incident visibility, keys, retention, and ledger identities across tenants. Current schema and authorization do not implement tenant boundaries. **Difficulty: Hard. Project/paper: Major architecture work. Infrastructure: PostgreSQL and security testing.**
9. **Disaster recovery and retention** — Define RPO/RTO, encrypted backups, restore drills, audit retention, and deletion/legal-hold policy. Current docs describe only local persistence. **Difficulty: Medium–Hard. Project/paper: Enterprise maturity. Infrastructure: Backup storage and recovery environment.**
10. **Security assurance program** — Threat modeling, dependency scanning, SBOM, code review rules, penetration testing, vulnerability response, and release signing. Current checks are unit/integration tests and a manual source audit. **Difficulty: Medium–Hard. Project/paper: Required before external deployment. Infrastructure: CI/security tooling and review process.**

## Strong candidates for a research paper extension

1. **Human-approved remediation safety:** evaluate policy/approval designs against false positives, decision latency, and simulated service impact using a reproducible Kubernetes testbed.
2. **Condition correlation under partial failure:** compare persistent fingerprint strategies, duplicate suppression, and reappearance handling across noisy or incomplete cluster observations.
3. **Calibrated incident triage:** establish a properly sourced dataset and compare calibrated ML baselines, rules, and deterministic policy outcomes with per-class metrics and drift tests.
4. **Privacy-preserving integrity evidence:** compare metadata-only ledger commitments, off-chain evidence custody, privacy exposure, verification cost, and retention/governance constraints.
5. **Hybrid PQC incident provenance:** measure signing/verification and envelope overhead for ML-DSA/ML-KEM integrated with incident records, including key rotation and verification failures.

A credible paper extension needs a defined research question, a threat model, baselines, reproducible data/code, evaluation metrics, and honest negative results. Merely connecting another service is not a research result.
