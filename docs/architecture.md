# QuantumSHIELD architecture

```text
Authenticated React client
        |
FastAPI authentication/RBAC + incident API
        |-- SQLAlchemy -> SQLite locally / PostgreSQL when configured
        |-- AI client -> separate FastAPI/scikit-learn service
        |-- PQC service -> optional liboqs ML-DSA / ML-KEM
        |-- blockchain client -> process-local mock OR authenticated Node bridge -> Fabric Gateway
        |-- Kubernetes observer -> REST API, explicitly labeled mock, or unavailable
        |-- detector -> normalized operational/security-relevant conditions -> deduplicated incident intake
        `-- response policy -> allowlisted Deployment action -> simulation by default / gated real execution
```

## Incident lifecycle

`POST /api/v1/incidents` validates an authenticated event and commits its initial record and creation audit event. The API calls the configured AI service and validates the response. An unavailable or invalid AI response is recorded as such; the event remains available with severity `unknown`. It records the severity and healing policy decisions, canonicalizes the security record, calculates SHA-256, and attempts ML-DSA signing and verification when an OQS provider is configured. Each status records whether an operation succeeded, failed, was unavailable, or was not performed. If evidence encryption is requested, the API requires the provider and recipient key before persisting the incident, uses ML-KEM to establish a shared key and AES-256-GCM to encrypt the canonical evidence record, and does not store the original description in plaintext. A runtime encryption failure also does not retain the description. The policy creates a simulation-mode healing action; no cluster operation is executed. Finally, it optionally writes an integrity metadata record to the configured ledger adapter and records the result.

Hashes and signatures cover the canonical record, including a digest and the evidence text. A hash is not encryption. ML-DSA verifies authenticity/integrity; ML-KEM is key establishment only. The authenticated symmetric encryption is what encrypts the evidence. AI analysis receives the event description before storage encryption; configure `AI_SERVICE_URL` to use TLS when the AI service is remote.

## Roles and permissions

- **Administrator:** granted every declared permission; initial administrator is provisioned through the interactive local CLI. Public user-management/role-change endpoints are not implemented.
- **Security Analyst:** create/read incidents, request analysis, update triage status, and read audit trails.
- **Operator:** create/read incidents and update eligible incident status. Response-execution permissions are reserved for the Phase 3 response API.

Public registration creates only Security Analyst accounts. Bearer tokens are checked against the persistent active user record, so deactivation or role changes take effect immediately.

## Integrations

The AI service loads a model artifact generated by `python -m ai_engine.train`. Its synthetic dataset is demo-only. Confidence is the classifier's class probability and is explicitly uncalibrated.

`PQC_PROVIDER=unavailable` is the default. `PQC_PROVIDER=oqs` requires `PQC_PRIVATE_KEY_PATH` and `PQC_PUBLIC_KEY_PATH`; encryption additionally requires `PQC_RECIPIENT_PUBLIC_KEY_PATH`, and decryption requires `PQC_KEM_PRIVATE_KEY_PATH`. Keys are provisioned externally and are never generated into or copied into this repository.

`BLOCKCHAIN_PROVIDER=mock` is the development default. The process-local mock supports record, retrieve, existence, and integrity checks; it reports provider `mock` and status `mock_recorded`, never `fabric`. `disabled` skips recording. `fabric` calls the authenticated Node bridge; the bridge requires a live configured peer, identity, channel, deployed chaincode, and `BLOCKCHAIN_API_TOKEN`. The chaincode records metadata and integrity hash, not raw evidence. Mock records do not survive process restart.

## Phase 3 Kubernetes and response lifecycle

`configured_provider()` returns unavailable unless an explicit provider is selected. The real observer uses the Kubernetes HTTPS REST API with a bearer token and trusted CA; the mock provider labels itself as mock and is used only for tests/demo. The interface exposes health, nodes, namespaces, pods, Deployments, events, and a small Deployment mutation interface. It does not expose raw HTTP paths or arbitrary commands to API clients.

`POST /api/v1/kubernetes/poll` takes one observation snapshot, evaluates restart, crash-loop, pod health, Deployment readiness, node readiness, and configured event-reason rules. Findings are normalized with deterministic fingerprints. Active fingerprints are suppressed on later polls; each new condition is submitted through the Phase 2 incident pipeline, which performs AI analysis, severity decision, audit, PQC integrity, and optional ledger recording. Rule output uses operational-anomaly/security-relevant-event terminology; AI analysis may separately classify the incident.

The response policy returns its decision and reason. Low severity is record-only; medium recommends operator action; high and critical require explicit approval. No severity value alone permits execution. The action set contains only restart and scale Deployment. Namespace and Deployment names must match DNS-label validation and separate server-side allowlists. Scale is bounded by `KUBERNETES_MAX_REPLICAS`. Simulation is the default path; a simulation action records that no mutation occurred and verification is `SIMULATION`.

Real execution requires an authenticated operator/administrator, explicit approval in the request, policy permission, `KUBERNETES_REMEDIATION_ENABLED=true`, a real REST provider, allowlisted resources, and a supported action. After a successful API call, the Deployment is read again and checked against the requested outcome. Execution and verification are separate audit events. Provider errors, timeouts, and verification failures do not become success. A canonical response evidence record receives a SHA-256 hash, optional PQC signature/verification, and an optional separate mock/Fabric ledger record.

## Phase 4 persistent watch and approvals

The optional `KubernetesWatchService` is created from the FastAPI lifespan only when `KUBERNETES_WATCH_ENABLED=true`. It sleeps for the configured interval, uses `configured_provider()`, opens a fresh database session per poll, and calls the same `poll_and_create_incidents()` path as the manual API. It records watcher start, tick, error, and stop events. Shutdown signals the task and waits for it. Polling errors are audited and do not resolve existing findings.

Each complete successful snapshot is normalized once and passed to detection. The fingerprint hashes cluster identity, condition type, namespace, resource, and stable condition title; volatile evidence such as counts or event messages do not change identity. A unique fingerprint row records status, first/last observation, occurrence count, latest evidence, and incident association. An active repeat updates the row and audit record without an incident. Absence from a successful complete snapshot resolves an active row. Reappearance changes it back to active and creates a new incident while retaining its historical count. This is the documented new-occurrence rule. The database unique constraint prevents duplicate rows across process restarts.

Policy remains advisory and is reevaluated independently of approval. An approval row binds a specific incident, action, resource parameters, policy decision, requester, expiry, and decision actor. Analysts may request; only operators and administrators may decide or execute. Separation of duties blocks self-approval when enabled. Real mutation also requires the global gate, server allowlists, action validation, policy allowance, a current matching unconsumed approval, and the bounded REST provider operation. Each block reason is recorded. Simulation bypasses approval only because it never calls a mutating provider method.

After a real action, the service re-reads Deployment state up to `KUBERNETES_VERIFICATION_MAX_ATTEMPTS`, waiting at most the configured delay between attempts. It records each check. Desired generation/readiness is required for `VERIFIED`; exhausted nonconvergence becomes `TIMEOUT`, and provider errors remain `UNAVAILABLE`. API acceptance is not considered convergence.

When `DEMO_MODE=true`, the deterministic provider and classifier are selected and the blockchain client is forced to its process-local mock. PQC is explicitly unavailable in this mode. Demo observations, classifications, remediations, and ledger records are simulated and are not claims about live services. The demo requires no Kubernetes, Fabric, or liboqs installation.
